Problem 01: Microservices Deployment, E-Commerce Workloads, CPU Throttling, and Cluster Monitoring

1. Project Overview & Architecture

In cloud computing environments, applications must coexist on shared physical nodes without causing resource starvation or node crashes. This project implements a full-featured E-Commerce Microservice ("CloudCommerce") deployed on Kubernetes, integrated with a Real-Time Cluster Monitoring Dashboard.

💡 The Core Problem Solved

When traffic surges during a "Flash Sale", how does Kubernetes protect the node? CPU Requests guarantee placement reservations, while CPU Limits trigger Linux CFS quota throttling (degrading response time from ~35ms to ~390ms without crashing). In contrast, Memory Limits enforce a hard ceiling: any memory spike beyond the limit triggers the Linux kernel OOM Killer (Exit Code 137), forcing container restarts.

2. E-Commerce Microservice Features

  • Product Catalog: Dynamic listing with search, category filtering (Servers, AI Accelerators, Gear, Merch), and live stock counts.
  • Shopping Cart: Real-time item additions, quantity updates, subtotal, and tax calculations.
  • Checkout Flow: Simulated payment & order processing, unique order ID generation (ORD-XXXX), inventory reduction, and order history tracking.
  • Built-in Cluster Monitoring Dashboard: Tab directly in the web app showing live CPU%, RAM RSS (MB), Downward API Pod/Node metadata, and request latency.
  • Flash Sale Traffic Generator: Injects high-concurrency synthetic buyer traffic (20 to 50 concurrent shoppers) to push cluster resource utilization in real time!
  • Prometheus Exporter: Standard /metrics endpoint exposing request counts, order totals, and process memory for external Prometheus scraping.

5. Top Viva Voce Questions & Answers

Q1: What is the difference between CPU Requests and CPU Limits?
Answer: Requests are evaluated by the Kubernetes Scheduler to determine node placement. Limits are enforced at runtime by the Linux kernel cgroups to cap maximum resource consumption.
Q2: Why does an application get slower under CPU limits instead of crashing?
Answer: CPU is a compressible resource. The Linux Completely Fair Scheduler (CFS) enforces a quota on CPU execution time slices. When the quota is reached, execution is paused until the next CFS period, increasing latency without terminating the pod.
Q3: Why does exceeding memory limits trigger OOMKilled with Exit Code 137?
Answer: Memory is an incompressible resource. When physical RAM limits are exceeded, the Linux kernel invokes the OOM Killer and sends SIGKILL (Signal 9). Exit codes for signals are calculated as $128 + 9 = 137$.
Q4: How does our monitoring dashboard read pod limits without cluster admin rights?
Answer: Using the Kubernetes Downward API (`resourceFieldRef`), which dynamically injects container requests and limits as environment variables directly inside the running pod.
Q5: In what sequence does Kubelet evict pods during node memory pressure?
Answer: Kubelet evicts BestEffort pods first, followed by Burstable pods that exceed their requested memory. Guaranteed pods are protected and evicted last.
